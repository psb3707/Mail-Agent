# mail-agent — 메일함을 건(件) 단위로 재조립하는 레이어

> 해커톤: 당일 7시간 / 2명 / 발표 10분(시연 3~4분) / 라이브 시연

## Context — 문제의 본질

임직원이 말하는 불편은 다섯 가지다. 정리가 안 되고 쌓이기만 한다 / 어떤 메일에 어떤 첨부가
있는지 모른다 / 관련 있어 보이는 메일을 하나씩 뒤진다 / 이전에 뭐라고 답이 왔는지 직접 찾아야 한다 /
메일함 용량이 부족하다.

드릴다운하면 하나의 명제로 수렴한다.

> ## 메일함은 보관은 하지만 정리는 하지 않는다.
> ### 그 정리 비용을 매번 사람이 낸다.

구조적으로 말하면 — **메일은 '통' 단위로 도착하는데, 일은 '건' 단위로 돌아간다.**
메일함은 아카이브가 아니라 **도착 로그(arrival log)** 여서, 시간순으로 쌓기만 할 뿐
"무슨 일이 있었는지"는 기록하지 않는다. 통을 건으로 재조립하는 작업을 지금까지
사람의 기억이 담당했고, **기억은 쌓이는 메일을 감당하지 못한다.**

### 이 규정이 증상 다섯을 모두 설명한다

| 증상 | 본질과의 연결 |
|---|---|
| 쌓이기만 함 | 시간순 로그는 원래 쌓이는 구조. 정리 기준(=건)이 없음 |
| 어떤 첨부가 있는지 모름 | 첨부는 *메일에* 붙어 있지 *건에* 붙어 있지 않음 |
| 하나씩 뒤져야 함 | 재조립 비용을 사람이 매번 지불 — 이게 "뒤진다"의 정체 |
| 이전 답변을 못 찾음 | 결정·합의가 로그에 흩어져 건 단위로 조회 불가 |
| 용량 부족 | 무엇을 지워도 되는지는 건 단위로 봐야 판단 가능. 못 보니 다 남기거나 다 지움 |

다섯 번째가 별개 불편처럼 보이지만 같은 뿌리라는 점이 이 규정의 타당성을 보여준다.

### 해법의 정의

> **메일함을 도착순이 아니라 건(件) 단위로 보게 하는 레이어**
> — 즉, **정리 비용을 사람이 아니라 기계가 내게 한다.**

분류는 건을 세우는 수단이고, 검색은 건에 도달하는 통로다. 모든 기능이 이 정의에 종속된다.

### 왜 하필 지금인가 (AI 타당성의 핵심 논거)

메일을 시간이 아닌 건으로 재조립하려면 **"이 메일들이 같은 건인가"** 를 판단해야 한다.
제목이 다르고, 스레드가 끊기고, 축약어가 섞인 상태에서. 규칙으로는 불가능했고
그래서 20년간 사람의 기억이 담당했다. **기계가 이 판단을 하게 된 건 최근이다.**

같은 논리가 첨부에도 적용된다. 키워드 인덱싱은 예전에도 됐지만
*"이 문서가 내가 찾던 그 버전인가"* 는 열어봐야만 알 수 있었다.

## 심사 기준과의 정렬

| 기준 | 답 | 담당 장면 |
|---|---|---|
| 문제 규정 | 증상이 아니라 구조를 지목 ("통 vs 건") | 장면 1 |
| AI 적용 타당성 | 규칙으로 불가능한 판단만 AI에 맡김 (같은 건인가 / 같은 문서의 어느 버전인가) | 장면 2·4 |
| 실용성 | 심사자가 직접 막혀보고, 해결되는 걸 눈앞에서 확인 | 장면 1→3 |
| 허울 아님 | 원본 메일함 무수정, 사내 연동 경로와 반출 화이트리스트를 발표에 포함 | 슬라이드 |

**Gmail 반문 차단**: 데모 무대는 개인 Gmail이 아니라 가상 사내 메일 환경.
Gmail은 본문 전문검색이 강력해 "검색이 안 된다"는 전제를 스스로 무너뜨린다.
더 중요하게는 — Gmail도 **건 단위 재조립은 못 한다.** 스레드는 *회신 관계*지 *사안*이 아니다.

## 시연 (3~4분, 4장면 고정)

| # | 장면 | 길이 | 본질과의 연결 |
|---|---|---|---|
| 1 | **심사자에게 되묻기** — 실제 사내 메일 제목 30개를 띄우고 *"여기서 지난 분기 B사 견적서를 찾으려면 뭘 검색하시겠습니까?"* | 45초 | 도착 로그의 무력함을 **체감**시킴 |
| 2 | **건 단위 재조립** — 같은 메일함이 사안 카드 + 타임라인으로 전환 | 60초 | "통 → 건" 전환의 시각적 증명 |
| 3 | **첨부 정답 찾기** — 자연어 질문 → 문서 내용을 근거로 정답 제시 | 60초 | 건에 첨부가 붙어 있으니 도달 가능 |
| 4 | **버전 판별 (하이라이트)** — *"이 셋은 같은 문서의 다른 버전, 최신은 이것, 달라진 건 단가"* | 45초 | 사람이 못 하는 판단 = AI 타당성 |

### 장면 1을 심사자 참여형으로 하는 이유

데이터를 우리가 만들었으므로, 우리가 검색을 실패시켜 보이면
**"검색이 안 되게끔 데이터를 만든 것 아닌가"** 라는 반문에 무방비다.
심사자가 직접 막히면 조작 시비가 사라지고 문제가 그의 것이 된다. 구현 비용도 오히려 줄어든다.

발표 멘트: *"이건 저희 회사 실제 메일 제목입니다. 회사명만 가렸습니다."*
심사자가 답을 못 하거나 침묵하면 발표자가 자연스럽게 받아서 진행한다.

### 라이브 호출 정책

**장면 3·4는 라이브 호출이 기본.** 캐시는 *네트워크 장애 시 자동 폴백*으로만 쓴다.
대본 질문만 동작하는 게 들키면 "짜고 치는 데모"가 되고, 해커톤 심사에서
**"그럼 이건 찾아주나요?"** 라는 즉석 요구는 거의 반드시 나온다.
→ 리허설에서 **대본에 없는 질문 3개**를 던져 임의 질문 대응력을 확인한다.

## 아키텍처 (7시간 최소 구성)

```
[사전 준비]                      [당일]                    [라이브]
가상 메일 100통 (JSON)   →  색인 파이프라인 실행    →  단일 페이지 웹앱
가상 첨부 15~20개(PDF/xlsx)   (건 그룹핑 + 태깅         토글: 도착순 ↔ 건 단위
정답 세트                      + 첨부 텍스트 추출)      질문창 → 라이브 LLM
                             → indexed.json
```

**DB 없음** (100통에 SQLite는 순수 비용) · **어댑터 추상화 없음** (소스가 하나) ·
**규칙 엔진 없음** (절감할 비용이 없음) · **화면은 단일 페이지 토글** (구현량 절반, 대비 선명, 전환 사고 없음)

### 동적 유입 원칙 (증분 정리·분류)

분류는 "이미 쌓인 메일"의 1회성 색인이 아니라 **메일이 도착한 순간부터** 동작한다.
시연은 전체 배치로 실행하지만, 그 결과가 다음을 만족해야 한다.

- **순서 무관**: 메일이 어떤 순서로 도착해도 같은 건으로 묶인다. 도착 시각·정렬은
  분류의 결정 근거가 아니라 보조 단서일 뿐이다. (검증: 색인 입력 순서를 뒤섞어도
  같은 `cases[]`가 나오는지 재현 테스트로 확인)
- **멱등 재색인**: 신메일이 들어오면 전체 재색인을 수행해도 기존 건 ID·결론이
  흔들리지 않는다. 건 ID는 시퀀스가 아니라 콘텐츠·발신자 기반의 안정 키를 쓴다.
- **증분 편입**: 신메일은 ① 기존 건에 편입(가장 흔함) ② 새 건으로 시작 ③ 비건 처리
  셋 중 하나로 귀결된다. "어느 건에도 안 붙는 메일"의 처리 규칙이 분류의 일부다.
- **저장은 인메모리**: DB를 쓰지 않는 원칙에 따라 이 동적 구조는 세션/인메모리로만
  동작하고 영속화는 비범위로 둔다 (PoC 한정).

**비건(非件) 메일 처리 규칙** — 전체 메일의 대부분(현 데이터에서 400통 중 357통)은
건으로 묶이지 않는 공지·시스템 알림·개인 메일이다. 이들을 무시하지 않고 아래와 같이 처리한다.

| 구분 | 처리 | 화면 표시 |
|---|---|---|
| 시연 건(A·B·C·BG01~06) | 사안 카드로 재조립 | 건 단위 뷰 |
| 같은 패턴이 반복되는 알림(교육·보안·근태) | 유형별 접기(예: "러닝포털 알림 8통") | 하단 "알림" 섹션 |
| 그 외 단발성 공지·행정 | 건에 붙지 않으므로 무분류 유지 | "기타" 섹션 |

비건 처리는 "무엇이 건이고 무엇이 아닌가"라는 판단 자체를 시연 소재로 삼는다.

### 파일 구조

```
mail-agent/
  data/
    mails.json           # 가상 메일 100통 (사전 준비)
    attachments/         # 진짜 PDF/xlsx 15~20개 (사전 준비)
    indexed.json         # 색인 산출물: 건 그룹 + 태그 + 첨부 추출 텍스트
    demo_cache.json      # 폴백용 사전 계산 답변
  scripts/
    generate_data.py     # 가상 데이터 생성 (사전 준비)
    build_index.py       # 첨부 추출 + 건 그룹핑 + 태깅 → indexed.json
  app/
    main.py              # FastAPI — 라우트 3개 (/, /ask, /versions)
    grouping.py          # 건 단위 재조립 (장면 2)
    search.py            # 자연어 질의 → 후보 → 근거 (장면 3)
    versions.py          # 같은 문서 버전 판별 + 차이 요약 (장면 4)
    llm.py               # Claude 호출 + 실패 시 캐시 폴백
    templates/index.html # 단일 페이지 (토글 + 질문창 + 결과)
  slides/
```

### 장면 3·4의 동작

**장면 3** — ① 질문에서 단서 추출(상대사·문서종류·시기) LLM 1회 → ② `indexed.json`에서
후보 5~10개로 축소 → ③ 후보의 **추출된 내용**을 근거로 정답 선정 + 근거 문장 LLM 1회
→ ④ 정답 첨부 + **"왜 이것인가"**(문서 안의 실제 금액·일자·버전) + 원본 메일

**"왜 이것인가"가 데모의 심장이다.** 답만 던지면 신뢰가 안 간다.
문서 안의 실제 값을 인용해야 "열어보지 않고 판단"이 성립한다.

**장면 4** — 같은 건의 첨부들을 모아 동일 문서의 버전 계열을 판별하고,
최신본과 **직전 버전 대비 달라진 핵심 항목**을 제시한다.
`최종_최종_진짜최종.xlsx` 라는 보편적 고통에 정확히 대응한다.

## 사전 준비 (해커톤 전)

이 단계가 당일 7시간을 지킨다.

0. **동료 8~10명 미니 설문 (⚠️ 가장 가성비 높은 항목)**
   질문 두 개면 충분하다 — *"메일에서 예전 자료 찾는 데 보통 얼마나 걸리세요?"*,
   *"첨부가 내가 찾던 게 맞는지 확인하려고 열어본 적 있으세요?"*
   비용 프레임의 숫자가 **"저희가 측정했습니다"가 아니라 "임직원 10명에게 물었습니다"** 가 된다.
   심사 기준의 *"실제 임직원의 불편을 해소하는가"* 에 직접 답하는 근거이고, 개발 시간은 0이다.
   답변 중 인상적인 한 문장은 **발표에 직접 인용**한다.

1. **실제 메일 제목 20~30개 수집(익명화)** — 회사가 특정되는 고유명사만 치환하고
   말머리·축약어·표기 관행은 **그대로** 둔다. 리얼리티가 장면 1의 설득력 전부다.
2. **100통으로 확장 생성** — 씨앗 제목의 패턴을 유지. 하나의 건이 여러 메일에 걸쳐
   진행되도록 구성하고, **제목에 키워드가 없는 메일**을 의도적으로 포함(장면 1 성립 조건).
   300통은 화면에서 보이지도 않고 LLM 생성 티만 난다 → **100통, 품질 우선**
3. **진짜 PDF/엑셀 첨부 15~20개 생성** — 각 문서에 금액·버전·일자·상대사 등
   **근거로 인용할 실제 값**을 심는다. 장면 3·4의 재료다.
   **같은 문서의 버전 계열 3~4개를 반드시 포함**(장면 4 성립 조건).
4. **정답 세트 확정** — 시연 질문 3~4개 + 정답 첨부를 정하고 실제로 나오는지 확인.
5. **⚠️ 해커톤 규정 확인 (미확인 상태)** — 사전 코딩 허용 범위.
   아래 타임라인은 **가장 보수적인 가정**(데이터만 사전, 코드는 전부 당일)으로 짜여 있다.
   코드 사전 작성이 허용된다면 `build_index.py`와 페이지 골격을 미리 만들어
   0:30–1:30 슬롯을 통째로 회수하고, 그 시간을 즉석 질문 대응력과 완성도에 쓴다.

4:00에 장면 4가 안 되면 잘라내고 장면 1~3을 완성도 있게 간다.

**포기 순서**: ① 장면 4 버전 비교 → ② 사안 카드의 타임라인(카드만 유지) → ③ 장면 2를 정적 화면으로.
**장면 1과 3은 마지막까지 지킨다** — 이 둘이 없으면 발표 논리가 성립하지 않는다.

## 발표 구성 (10분)

1. **문제 (2분)** — *"메일함은 보관은 하지만 정리는 하지 않습니다. 그 정리 비용을 매번 사람이 냅니다."*
   → **동료 설문 숫자와 인용문**으로 비용을 실증 → 구조 지목: *"메일은 통으로 오는데, 일은 건으로 돌아갑니다"*
2. **시연 (4분)** — 4장면
3. **왜 AI인가 (2분)** — 규칙으로 시도했을 때 실패하는 실제 사례.
   그리고 **"왜 이제야 가능한가"** (같은 건 판단 / 같은 문서의 어느 버전인가)
4. **실용성과 확장 (2분)** — 사내 연동 경로(메일 시스템팀과 합의할 인터페이스 한 장),
   **반출 화이트리스트 보안 설계**, 용량 문제로의 확장(건 단위로 보면 무엇을 지울지 판단 가능)

보안 설계는 구현하지 않고 슬라이드 한 장으로 다룬다. 사내 도입을 염두에 뒀다는 신호가 목적이고,
7시간 안에 구현할 가치는 없다.

**`measure.py` 자체 측정은 하지 않는다.** 우리가 우리를 상대로 잰 "3분 20초 → 12초"는
심사자가 믿지 않고, N=2 자체 측정이 드러나면 오히려 감점이다.
**장면 1에서 심사자가 직접 막힌 그 시간이 Before다.** 체험이 자체 측정보다 강하다.

## 검증

- **리허설 2회** — 4장면을 시간 안에 완주
- **즉석 질문 테스트** — 대본에 없는 질문 3개로 임의 대응력 확인
- **폴백 확인** — 네트워크를 끊고 장면 3·4가 캐시로 동작하는지
- **녹화 백업** — 완주 시연을 녹화해두고 라이브 실패 시 즉시 전환
