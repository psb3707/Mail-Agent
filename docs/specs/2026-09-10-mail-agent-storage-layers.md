# mail-agent — 저장소 3계층 구조 (원본 / 분류 뷰 / 에이전트 매니페스트)

> 대화방 인사이트 정리 · 2026-09-10
> 주제: 분류AI와 맥락 이해 Agent를 만들 때, 각자의 파일구조를 따로 가져갈지
> 아니면 애초부터 Agent가 이해하기 좋은 구조를 가져갈지에 대한 판단.

## 명제

"따로 구성"과 "Agent-friendly 구조"는 대립이 아니라 **층(layer)이 다른 문제**다.
한 구조에 사람 UX와 에이전트 성능을 섞으면 두 문제 모두 나빠지므로,
역할이 다른 **세 저장소**로 나눈다.

## 핵심 — 3계층 구조

| 계층 | 역할 | 성질 |
|---|---|---|
| ① 원본 메일 저장소 | 실제 데이터의 기준 | **불변(append-only)**, 안정 메일 ID |
| ② 분류 트리 | 사용자가 보는 탐색 뷰 | **파생물**, 심볼릭 링크, 언제든 재생성 |
| ③ 에이전트 매니페스트 | Agent가 읽는 지식 레이어 | **indexed.json**, 메타+트리+첨부 텍스트 |

### ① 원본 메일 저장소 — 불변
- 파일명 = **안정 메일 ID**(해시 기반, 예: `m_9f3a2c.json`). 도착 순서·분류와 무관.
- 절대 수정·이동하지 않음. `reply_to`, 발신자/일시/수신인/제목/본문 메타 전부 여기.
- "기준"이 이 계층이라야 분류 트리가 멋대로 바뀌어도 원본은 안전하다.
- 이 프로젝트의 AGENTS.md 원칙("절대 원본 메일함 데이터를 수정하지 않는다")과 정확히 일치.

### ② 분류 트리 — 파생물 (심볼릭 링크)
- 사용자가 보는 "파일시스템" 뷰. 카테고리/주제별 폴더에 **심볼릭 링크만** 들어감.
- **언제든 날려도 다시 만들 수 있는 것**. 분류기가 바뀌면 재생성.
- `build_index.py`에서 트리 구조를 결정해 생성하는 파생 산출물.

### ③ 에이전트 매니페스트 — indexed.json
- 에이전트(분류AI, 검색 Agent)가 **읽기 좋은** 형태의 메타데이터.
- `indexed.json`: 메일 메타 + 트리 구조 + 첨부 텍스트(추출 전문) + 건 그룹핑.
- 이것이 "Agent가 이해하기 좋은 구조"의 실체. 파일시스템 트리만으로는 수백 개
  심볼릭 링크를 뒤지는 비효율이 있어 Agent가 읽기 어렵다.

## 질문에 대한 직접 답

> 각자의 파일구조를 따로 구성하는 게 좋을까, 애초부터 Agent가 이해하기 좋은 구조를 가져갈까?

**둘 다 필요하되 "원본"은 사람 중심/불변, "분류 뷰"는 사용자 UX, "매니페스트"는 Agent용**으로
분리하는 것이 정답이다. 한 구조에 섞으면 원본 보존과 Agent 성능이 모두 나빠진다.

> 실제 메일은 따로 저장되고 분류시스템에는 심볼릭 링크가 들어가겠지?

**그렇다.** 그리고 그 심볼릭 링크 뷰는 "원본의 파생물"로 취급한다 — 실제 데이터가 아니라
사용자에게 보여주는 탐색용 가상 뷰이며, 재색인으로 언제든 다시 만들 수 있다.

## 기존 설계와의 정합성

이미 AGENTS.md와 설계 문서가 이 방향을 명시하고 있다.
- `data/mails.json`(원본, 400통) ↔ `data/indexed.json`(에이전트 매니페스트) 분리
- `build_index.py` = 심볼릭 링크 뷰 + indexed.json을 함께 만드는 파생 단계
- "동적 유입, 멱등 재색인" 원칙 = 분류 뷰가 언제든 재생성 가능해야 한다는 뜻

즉 이 인사이트는 기존 설계와 같은 축에 있으며, 실질적인 차이는
**실제 심볼릭 링크를 쓸지, 가상 트리(메타데이터만)로 할지**다.

## 실무적 권고: 실제 심볼릭 링크 vs 가상 트리

| | 실제 심볼릭 링크 | 가상 트리(indexed.json) |
|---|---|---|
| 사용자 UX | OS 파일탐색기에서 자연스러움 | 웹 UI에서 자연스러움 |
| Agent 접근성 | 나쁨(링크 뒤지기 어려움) | 좋음(JSON으로 바로 읽음) |
| 재생성/멱등 | 링크 지우고 다시 만들어야 함 | JSON 재빌드로 끝 |
| 포팅(Windows) | 심볼릭 링크 권한 이슈 | 무관 |

**권고**: PoC/데모 단계에서는 **실제 심볼릭 링크 대신 가상 트리(indexed.json)** 를 주력으로 하고,
"파일시스템처럼 보이는" 탐색은 UI에서 구현한다. Windows 환경에서 실제 심볼릭 링크는
관리자 권한 문제가 흔하고, Agent가 읽기엔 JSON이 훨씬 좋다.
"OS 탐색기에서 직접 파일처럼 보고 싶다"는 요구가 생기면 그때 실제 링크 뷰를 추가한다.

## 정리

- **원본**: 불변, 안정 ID, 실제 데이터
- **분류**: 파생 가상 트리(또는 선택적으로 실제 심볼릭 링크), 사용자 UX용
- **에이전트**: indexed.json 매니페스트가 "Agent가 이해하기 좋은 구조"의 전부
